# IIDX 34 (`2026091600-010`) port notes

Support for the 34th-generation `bm2dx.dll` build **2026091600-010** on top of the
33rd-gen `iidx33` branch. The 33rd-gen profiles are untouched.

## Target

| field | value |
|---|---|
| `E:\IIDX\ZINRAI\contents\bm2dx.dll` | 18 200 216 bytes |
| SHA-256 | `3755587f44785effe5008f74cfe7dccbdf423ad09feead48e00a90f78a42fe83` |
| `SizeOfCode` / `AddressOfEntryPoint` / `SizeOfImage` | `0x00C64200` / `0x00B02B3C` / `0x0C5FF000` |
| `music_data.bin` header | magic `IIDX`, version **34**, 1970 entries, 35 000 occupied 鈫?`MAX_ENTRIES = 0x88B8` |

The reference 33rd-gen binary used for the transfer is
`bm2dx.dll` build 2026081900-010 (`0x0C8F800 / 0x0B1CCCC / 0x0BB95000`,
SHA-256 `46516b4b64b2e6689aaf5b411da59e1de2b74456009d290b418e8aea3a780f1b`).

## Method

Every address was produced by **masked code-signature transfer** between the two
builds (RIP-relative displacements and `call`/`jmp` rel32 operands wildcarded),
then checked against the instruction at the same site in the reference binary:

1. locate the containing function of the 33rd-gen offset, transfer the whole
   function by signature, re-add the intra-function delta;
2. fall back to instruction windows ending at the site, then to byte patterns;
3. for virtual functions use MSVC RTTI: type descriptor 鈫?complete object
   locator 鈫?vtable 鈫?slot, and align slots across builds;
4. for globals: transfer every instruction that references the old address,
   recompute the new RIP-relative target, and take a vote.

The tooling lives in `re/` (`iidxre.py`, `port.py`, `vtslots.py`, `pat.py`,
`verify_final.py`); `re/verify_final.txt` is the current report (82/82 offsets
decode on an instruction boundary inside `.text`/`.data`/`.rdata`).

### Vtable slot shift (important)

IIDX 34 inserted three virtuals into the common scene base class. Every scene
vtable slot **鈮?13 moved by +3**:

| field | 33rd-gen slot | 34 slot | 34 address |
|---|---|---|---|
| `DAN_SELECT_CTOR` (`CDanSelectScene`) | 13 | 16 | `0x8B9CC0` |
| `STAGE_RESULT_FN` (`CStageResultScene`) | 13 | 16 | `0x914080` |
| `MDATA_LOAD_FN` (`CMonitorCheckScene`) | 15 | 18 | `0x91AF40` |

`STAGE_RESULT_FN` was independently confirmed by disassembling the scene-enter
body; `MDATA_LOAD_FN` was independently recovered by signature transfer. Do not
reuse 33rd-gen slot numbers when adding the next build.

`CARD_OUT_VFUNC` is the **address of the vtable slot** (2dxtra overwrites the
pointer), not the function: `CCardOutScene` vftable = `0xD46608`.

## Data offsets that changed shape

* The renderer/app manager moved to the heap: `D3D9_DEVICE` is no longer a fixed
  address. The static at `0xB4E3360` holds the manager pointer and the
  `IDirect3DDevice9*` is its `+0xE0` field, so the profile uses
  `D3D9_MANAGER_PTR` and `bm2dx::d3d9_device()` resolves it at runtime.
* The per-player game-data block stride grew from `0x3B103A0` to `0x3E66DB8`;
  `PLAYER_BLOCK` (`0x328C068`) is verified by `RESET_STATE_FN`, which memsets
  exactly `stride` bytes at `PLAYER_BLOCK + player * stride`.
* `AUTO_PLAY` (`0xB3CABBC`) is verified by the game's own initialiser, which
  stores `0x100` into that word right after `AUTO_PLAY - 4`.

## Struct layout checks

`game.h`'s structs are a prefix view of the game's objects, so what matters is
the field offsets 2dxtra reads and writes. Two independent checks were used:
the shape of the data itself and the offsets the 34 build hard-codes.

| struct | evidence |
|---|---|
| `music_data_t` / `music_entry_t` | parsed `data/info/0/music_data.bin`: magic `IIDX`, version 34, 1970 entries, 35000 occupied; entry array starts exactly at `0x10 + 4*35000`; four entries decode with title/ascii/genre/artist at `0x0/0x100/0x140/0x1C0`, `id` at `0x67C`, `volume` at `0x680`, stride `0x7F8` |
| `state_t` | direct accesses in both builds: `+0x00/+0x04/+0x10/+0x14/+0x5C/+0x70` - identical sets |
| `play_state_t` | the set of offsets the game uses on the `PLAY_STATE` pointer is *identical* in both builds (`0x6,0x8,0x10,0x18,0x20,0x24,...,0x394,0x6E0,...,0xA50,0xA58,0xA68,0xA70,...`) - `players` at `0x10` and `pacemaker_target` at `0xA68` are both in that set |
| `play_session_t` | identical set up to `0xAC0` (`0x4..0x2D,0x34,0x40,0x44,0x48,0x58,0x88,0x94,0xA0,0xB0,0xC8,0x100,0x8B8,0xAC0`), so `in_gameplay 0x54`, `ready 0x88`, `current_score_pb 0x414`, `pacemaker_type_id 0x440` are unchanged; the only growth is a `+0x20` shift above `0x10D0` |
| `CApplicationConfig` | `GET_APP_CONFIG` callers use the same offsets in both builds, including `target_fps 0x14` and `monitor_check_fps 0x1C` |
| `text_props_t` | `TEXT_INIT_FN` writes the identical offset sequence in both builds |
| `InputManagerIIDX` / `input_t` | `INPUT_POLL_FN` writes the identical offsets in both builds; the vtable pointer check is also done at runtime |
| `random_data_t` | `APPLY_RANDOM_FN` is instruction-for-instruction identical (226/226 normalised instructions) |
| `lane_cover_control` | `cover_visible` at `0x28` is confirmed by the patch site itself (`xor byte ptr [rsi+28h], 1`) |

`re/seqcmp.py` compares normalised instruction streams: the hooked functions
that hard-code these layouts score 1.000 (`APPLY_RANDOM_FN`, `JUDGE_DISPLAY_FN`,
`RETRY_CHECK_A`, `MDATA_LOAD_FN`, `RESET_STATE_FN`, `SCORE_INVALID_FN`,
`GET_SAVED_HI_SPEED`), and the two scene entries picked by the vtable mapping
score 0.88 / 0.81 (a wrong slot would be ~0.1).

`IS_SEPARATE_SCRATCH_FN` (`0x7F48F0`) keeps the exact 11-instruction prefix of
the 33rd-gen accessor and calls the same three helpers, but the 34 build
implements the tail as a jump table instead of two compares, so its return
values are only medium confidence.

## Diagnostics

`2dxtra.log` (next to the DLL, appended) records:

- which profile matched (or that none did) and the address of every resolved global;
- every hook install step, so a crash points at the last line;
- `probe: game model "***:*:*:*:**********" ok|MISMATCH` - proves `GAME_MODEL`;
- `probe: input manager vtable ok|MISMATCH` - proves `INPUT_MANAGER` by checking
  that its vtable slot 3 is `INPUT_POLL_FN`;
- `probe: config target_fps ...` and `probe: state ...` - plausibility of those globals;
- `music_data ... magic IIDX entries ... occupied ...` - proves the music blob;
- `result sample ...` - the first four result-screen score reads, so a wrong
  score-table base shows up as impossible values instead of silent corruption;
- `score isolation enabled|DISABLED`.
## Diagnostics

`2dxtra.log` (next to the DLL, appended) records which profile matched, the
address of every resolved global, each hook install step and whether score

## Score / rival tables (34th gen)

The 33rd-gen profile addresses the score tables as offsets inside the
per-player block array, so the same displacements were recovered from the one
instruction idiom that indexes them (`lea rax,[r8+r8*2]; add rax,rax;
cmp byte [base + rax*8 + disp]` → 6 rivals × 0x30-byte entries):

| field | 34 value | derivation |
|---|---|---|
| `SCORES_P1` | `0x32BADD4` | `mov ecx,[r9+rdx*4+0x223ECE4]` at `0x594BE1` (unique match of the 33rd-gen `0x5A3BB1` idiom) + block array `0x107C0F0` |
| `SCORES_P2` | `0x36A158C` | `SCORES_P1 + 0x3E66DB8` (per-player stride, same relation as the 33rd gen) |
| `RIVAL_SCORES_P1` | `0x3B35D78` | `cmp byte [.. + 0x2BDBCB5]` at `0x598A0F` (rival accessor, instruction-for-instruction identical to the 33rd-gen one) minus `0x2D` (`is_populated`), + block array |
| `RIVAL_SCORES_P2` | `0x3F1CB30` | `+ 0x3E66DB8` |

The `SCORES_P1` base is confirmed a third time by the field pattern the 34 build
itself uses relative to `0x223ECE4`:

| displacement | `game_score_t` field | site |
|---|---|---|
| `+0x00` | `score[0]` | `0x594BE9` |
| `+0x14` | `miss[0]` | `0x594C0F` |
| `+0x1C` | `miss[2]` | `0x5A6224` |
| `+0x28` | `clear[0]` | `0x594BD2` |
| `+0x2D` | `is_populated` | `0x594BA5` |

Those are exactly the offsets `game.h` declares, so `0x223ECE4` is the base of a
`game_score_t` array and `SCORES_P1` / `SCORES_P2` follow from it.
`MAX_ENTRIES` is `0x88B8` (35000), confirmed twice: the `music_data.bin`
index table and the `imul r8, rdx, 0x88b8` in the rival accessor.

Also resolved in this pass:

| offset | 34 value | evidence |
|---|---|---|
| `IS_SEPARATE_SCRATCH_FN` | `0x7F48F0` | calls the option getter that reads `[block+0x68]` (`0x882CE0`); field offset unchanged in 34 |
| `HI_SPEED_ADJUST_CALL` | `0x8F6716` | the double-START handler `0x8F66E0` is instruction-for-instruction identical to the 33rd-gen `0x90B8F0`, and the call sits at `+0x36` in both |

The renderer/app manager is heap-allocated in the 34th gen, so `D3D9_DEVICE`
stays `nullptr` and `D3D9_MANAGER_PTR` (`0xB4E3360`) is used instead:
`*(void**)D3D9_MANAGER_PTR + 0xE0` is the `IDirect3DDevice9*`.

## Verification

`re/verify_final.py` decodes every non-null offset against the target binary:
88/88 land on an instruction boundary inside `.text`/`.data`/`.rdata`
(`re/verify_final.txt`).

`re/resolve_check.cpp` builds a small console program against the **generated**
`macros/offsets.h` (the exact table the DLL ships). It maps a `bm2dx.dll` as an
image, calls `resolve_offsets()` and spot-checks 18 hook sites:

| binary | result |
|---|---|
| 34 target `2026091600-010` | `matched 2026091600-010`, all spot checks passed |
| 33rd-gen `2026081900-010` | `matched 2026081900-010`, all spot checks passed (no regression) |
| `bm2dx0909.dll` (34-era, unsupported) | no profile matched, DLL refuses to load as before |

Still missing: an actual in-game session on 34. Everything that can be proven
statically is green; the three paths that were degraded in the first build

## Runtime evidence

First boot with `-k 2dxtra.dll` on the target build (2026-10-25 22:59), excerpt
from `2dxtra.log`:

```
[2026-10-25 22:59:20] loaded against 2026091600-010 (2dxtra 7.2.0)
[2026-10-25 22:59:20] probe: game model "***:*:*:*:**********" ok
[2026-10-25 22:59:20]   profile 2026091600-010  base 000000000E980000  max_entries 0x88b8
[2026-10-25 22:59:20]   state 0000000019F8B3A0  config 0000000019F8C6C8  input 000000001A64E280
[2026-10-25 22:59:20] probe: input manager vtable ok
[2026-10-25 22:59:20]   score isolation enabled
[2026-10-25 22:59:20] ... 23 hook installs ...
[2026-10-25 22:59:20] init complete
[2026-10-25 23:01:18] music_data 0000000019F8C870 magic IIDX entries 1970 occupied 35000 max_entries 0x88b8
```

* the DLL resolved the profile at the relocated base `0xE980000` (RVA based, so
  the non-preferred load address is fine);
* every hook installed and the game kept running;
* the chart database was built from scratch (0 -> 543 MB) while the game was
  live, which exercises `LOAD_CHART_FN_A/B`, `CHART_ANALYZE_FN` and
  `CHART_CALC_RADAR_FN` end to end;
* the music_data blob was read back with the expected header and entry count,
  confirming `GET_MUSIC_DATA` and `MAX_ENTRIES = 0x88B8`;
* spice2x reports `game version: LDJ:J:D:E:2026091700` - the `E` is this DLL's
  soft-revision patch (`SOFT_REV_PATCH`) taking effect. The in-game build id is
  `2026091700`; the profile keeps the `2026091600-010` name the fork already
  used, the PE triple is the real discriminator;
* no 2dxtra-related errors in `log.txt`; the session ended through
  Alt+F4 (clean exit).

A second boot of the same build confirmed the timeline: `init complete` 20 s
after launch, then `music_data ... magic IIDX` and `probe(late): config
target_fps 120` - the app config is only populated once the game loads its
settings, which is why `DllMain` sees `target_fps 1`.

One real finding: `config->monitor_check_fps` reads `1.0` in the 34th gen
instead of the refresh rate. `fast_slow_hook` uses it for the half-tick shift of
the millisecond display, and `1000 / 1.0 / 2` would have shifted the numbers by
half a second, so the hook now falls back to `target_fps` whenever the value
cannot be a refresh rate (< 30).

## Build

MSVC 14.44 + Windows SDK 10.0.26100 + Ninja, static CRT, vcpkg
`x64-windows-static-pz` triplet with manifest mode off (same toolchain as the
`iidx_hyper_recording` tree in this workspace):

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_MAKE_PROGRAM=.../ninja.exe \
  -DCMAKE_TOOLCHAIN_FILE=.../vcpkg/scripts/buildsystems/vcpkg.cmake \
  -DVCPKG_TARGET_TRIPLET=x64-windows-static-pz -DVCPKG_MANIFEST_MODE=OFF \
  -DVCPKG_INSTALLED_DIR=.../vcpkg/installed
cmake --build build
```

Output: `build/2dxtra.dll` (4 944 896 bytes,
SHA-256 `46516b4b64b2e6689aaf5b411da59e1de2b74456009d290b418e8aea3a780f1b`).
